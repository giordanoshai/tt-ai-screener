# 盯盘关键位提醒 —— 设计文档

**日期**：2026-09-04
**状态**：设计已确认，待写实现计划

---

## 一、要解决什么问题

### 真实案例（本设计的起点）

2026-09-04，用户持有 601138（工业富联）100 股，成本 61.52。

当天走势：
```
昨收 63.20  →  今开 63.84  →  盘中最高 65.30  →  回落到 63.55
```

用户的原话：**「今天到了一个关键的突破位，我不知道这是突破位，我没有卖，
导致到了突破位后就直接下跌了。」**

问题拆成两层：

1. **认知层**：用户不知道 64.84 这个价是一道坎（那是 8/31 的收盘高点）。
2. **通知层**：就算知道，也没有任何东西在盘中盯着，冲上去的那一刻没人叫他。

现有的 `watch_positions` 工具**两层都不解决**：

- 它只报**已经发生**的事（跌破止损、跌破 20 日均线、创 20 日新低），
  全是马后炮，没有「快到某个价位了」这种事前提醒。
- 它是**拉取式**的——用户在 Claude.ai 里开口问，它才跑一次。今天冲高的
  那一刻，没有任何进程在运行。

## 二、可行性验证（已完成，2026-09-04）

动手写代码之前先做了数据探测，结论如下。

### 2.1 关键位数据：够用，A 股比美股还全

以 601138 实测：三年日线 728 根，20/50/200 日均线、20 日最高价、
日均波动幅度（ATR）、量比、RSI 全部有值。

全市场填充率（2026-09-03 当天）：

| 市场 | 有数据的票 | 均线等指标填充率 |
|---|---|---|
| A 股 | 1,498 只/天（稳定） | **99.5%** |
| 美股 | 2,094 只/天 | 93.4% |

用户原本担心「A 股可能有点麻烦」——**实测相反，A 股这块比美股干净**。

### 2.2 实时行情：两条路都通，但各有坑

**A 股（AKTools，地址见 `.env` 的 `AKSHARE_BASE_URL`）**

| 接口 | 数据源 | 结果 |
|---|---|---|
| `stock_bid_ask_em` | 东方财富 | ❌ HTTP 500 |
| `stock_zh_a_spot_em` | 东方财富 | ❌ HTTP 500 |
| `stock_zh_a_hist_min_em` | 东方财富 | ❌ HTTP 500 |
| `stock_zh_index_spot_em` | 东方财富 | ❌ HTTP 500 |
| **`stock_zh_a_spot`** | **新浪** | ✅ 200，5,555 只，**15 秒** |
| `stock_zh_a_minute` | 新浪 | ✅ 200，0.97 秒 |

**坑 1：这台 AKTools 上东方财富源整个挂了**，所有 `_em` 后缀接口全部 500。
新浪源的全部正常。需要让 tt-data-hub 那边排查。
好消息是 `core/akshare.py` 用的正是新浪的 `stock_zh_a_minute`，**没受影响**。

**坑 2：小时线不能用来盯盘。** 新浪的小时线接口对**当天盘中**的 K 线
只给成交量、不给价格：

```
2026-09-03 15:00  open=63.54  high=63.79  low=63.01  close=63.20   ← 昨天，完整
2026-09-04 10:30  open=None   high=None   low=None   close=None    ← 今天，全空
2026-09-04 11:30  open=None   high=None   low=None   close=None    ← 今天，全空
```

所以 A 股盯盘**只能走全市场快照** `stock_zh_a_spot`，它有完整的
最新价/最高/最低/今开/昨收。一次 15 秒拿回全市场 5,555 只，
**盯 1 只和盯 5,000 只一样快**。

**美股（UW，走代理 `ai-tool.indevs.in/unusualwhales`）**

- **没有专门的「当前价」接口**：`/info`、`/quote`、`/price`、`/spot`
  四个路径全部返回 None。
- 实时价只能从 **1 分钟线的最新一根**取：`/api/stock/{票}/ohlc/1m`。
- **UW 返回的是倒序**（第一行最新，末行最老）。
- 单只票 11.4 秒，但**并发有效**：6 只持仓一起拉只要 **13.8 秒**。

**坑 3：美股是按票拉的，票越多越慢。** 156 只自选按这个速度要约 6 分钟
转一圈，所以第一版只盯持仓。

### 2.3 顺带发现的既存问题（不属于本设计，但要记一笔）

- 美股日线 2026-09-03 那天**只采到 106 只**（其他日子都是 2,094 只），
  上游那一趟明显没跑完。属于 tt-data-hub 的问题。
- AKTools 的东方财富源全挂，同上。

## 三、架构

### 3.1 新增文件

```
tt-trading-mcp/
  watchdog.py          ← 新增：盯盘守护进程，独立跑
  core/
    levels.py          ← 新增：关键位计算（纯函数，不碰数据库，好测）
    quotes.py          ← 新增：实时价获取，A股/美股两条路统一成一个接口
    notify.py          ← 新增：Telegram 推送
```

### 3.2 为什么是独立进程，而不是塞进 `main.py`

MCP 服务是给 Claude.ai 用的：用户重启它、改代码、它偶尔崩，
**都不应该让盯盘停掉**。反过来盯盘每分钟拉一轮行情，
也不该拖累 MCP 的响应速度。

两件事的失败模式完全不同，绑在一个进程里只会互相拖累。

### 3.3 每一轮做什么（每分钟一次）

```
1. 从 user_positions 读当前持仓
   ↑ 每轮都读，不在启动时写死。用户在 Claude.ai 里加仓/平仓，下一分钟生效。
2. 按市场分两拨取实时价：
     A 股 → AKTools 全市场快照，一次 15 秒
     美股 → UW 的 1 分钟线，并发拉，6 只约 14 秒
3. 跟当天的关键位比对
4. 触发了 → 查去重记录 → 没报过就推 Telegram
```

### 3.4 交易时段

**A 股只有盘中，美股有盘前盘后**——这是两个市场最大的区别，
合起来一天要盯 **20 小时**，北京时间 08:00–09:30、11:30–13:00、
15:00–16:00 是空的（A 股 15:00 收盘，美股盘前 16:00 才开始），共三段。

| 市场 / 时段 | 北京时间 | 时长 | 特殊处理 |
|---|---|---|---|
| A 股 上午 | 09:30–11:30 | 2.0h | — |
| A 股 下午 | 13:00–15:00 | 2.0h | — |
| 美股 盘前 | 16:00–21:30 | 5.5h | **门槛提高**，见下 |
| 美股 常规 | 21:30–04:00 | 6.5h | 主战场 |
| 美股 盘后 | 04:00–08:00 | 4.0h | 推送标注「盘后」 |

以上为美国夏令时；**冬令时美股三段各顺延 1 小时**（美国夏令时为 3 月第二个
周日至 11 月第一个周日，实现时按日期判断，不要写死）。

**盘前必须区别对待。** 实测 AAPL 连续三天的成交量分布：

| 日期 | 盘前 | 常规 | 盘后 |
|---|---|---|---|
| 2026-09-01 | **1.51%** | 80.75% | 17.74% |
| 2026-09-02 | **2.20%** | 80.98% | 16.82% |
| 2026-09-03 | **1.21%** | 75.49% | 23.30% |

盘前只占全天成交量的 1%~2%，几百股就能把价格打出去一大截，
这时候的「突破」极可能是假的。所以：

- **盘前**：要求连续 **3** 个采样点确认（常规时段 2 个），
  且**不做「有效突破」判定**（量能根本不可比）
- **盘后**：正常报，推送里标注「盘后」提醒流动性不如白天

判定时段**不要自己按时间猜**：UW 的 1 分钟线自带 `market_time` 字段，
`r` = 盘中、`pr` = 盘前、`po` = 盘后，直接用它。

**夜间不静音。** 美股常规时段（北京 21:30–04:00）正好压在睡觉时间上，
但那是成交量占 80% 的主战场，用户明确要求**全部照推**，
自己在手机上设免打扰。实现上不做任何夜间特殊逻辑。

关键位在每天各市场开盘前算一次（A 股 09:15，美股按盘前开始时间）放内存。

## 四、关键位算法 —— 本设计的核心

### 4.1 三版演进（都在真实数据上验证过）

用 601138 近 45 个交易日回放，**只用当天之前的数据算位**
（绝不能用当天或以后的数据倒推，否则回放结果会好得离谱但实盘没用）：

| 版本 | 做法 | 报警次数 | 多少天在响 | 今天抓到了吗 |
|---|---|---|---|---|
| 第一版 | 用**最高价**找位 | 40 次 | 71% | ❌ **漏了** |
| 第二版 | 改用**收盘价**找位 | 45 次 | 73% | ✅ 但太吵 |
| **第三版** | **+ 只推要动手的 + 去重** | **18 次** | **31%** | ✅ **抓到了** |

**第一版为什么漏掉今天**（这是本设计最重要的一课）：

```
08-28   开 64.04   最高 66.69   收 64.04     ← 冲到 66.69 全吐回来，一根长上影线
08-31   开 63.15   最高 65.00   收 64.84
09-01   开 64.35   最高 64.50   收 62.94
```

第一版用「近 10 天的最高价」，于是 8/28 那根插针的 66.69 **把下面的
65.00、64.50 全盖住了**。而今天只冲到 65.30，够不着 66.69，一声不响。

可 66.69 只是一瞬间摸到就吐光的价，它不是真正的阻力。真正的阻力是
8/31 **收在** 64.84 那个位置——市场真正认可、能收得住的价。

**结论：用收盘价找关键位，不用最高价。插针不算数，收得住才算数。**

### 4.2 最终规则

**阻力位（头顶的坎）**，三个尺度：

| 尺度 | 怎么算 |
|---|---|
| 近档 | 最近 25 个交易日里，**收盘价**的局部高点（前后各 2 天都不超过它） |
| 中档 | 最近 20 个交易日的最高收盘价 |
| 远档 | 最近 120 个交易日的收盘价局部高点（前后各 5 天），且**被测试过 ≥ 2 次** |

**支撑位（脚下的坎）**：完全对称，把「高点」换成「低点」。

**过滤规则**（缺一不可，每一条都是为了降噪）：

1. 只留方向正确的：阻力必须高于现价，支撑必须低于现价
2. 只留 **12% 以内**的：更远的今天碰不到，盯了也是浪费
3. 挨得近的合并：两个位相差 **1.2%** 以内算同一道坎
4. 上下**各只保留最近的 2 个**

对 601138，开盘前只盯 4 个价：

```
头顶  64.84   8/31 的收盘高点      距昨收 +2.6%   ← 今天撞的就是它
头顶  67.42   4/28 的高点          距昨收 +6.7%
脚下  62.16   4/30 的低点          距昨收 −1.6%
脚下  60.15   8/25 的低点          距昨收 −4.8%
```

### 4.3 每个关键位还要算一条「预警线」

**不能等价格摸到关键位才叫**——等摸到 64.84 才响，用户可能正在开会、
正在吃饭，等看到手机它已经冲上去又掉下来了。**提前响才有时间反应。**

每个关键位往回退 **1%** 画一条预警线：

```
关键位 64.84  →  预警线 64.19   （阻力：往下退 1%）
关键位 62.16  →  预警线 62.78   （支撑：往上退 1%）
```

选 1% 是拿数据比出来的（601138 近 45 个交易日）：

| 预警距离 | 预警条数 | 今天的预警线 | 问题 |
|---|---|---|---|
| 1.0% | 27 | 64.19 | ✅ 正合适 |
| 1.5% | 29 | 63.87 | 略早 |
| 2.0% | 30 | 63.54 | ❌ **开盘 63.84 就已越过，一开盘就叫** |

**预警必须是「穿越触发」，不是「在区间内就触发」。** 只有价格**从远处
走过来、穿过预警线的那一刻**才报；如果价格本来就在预警线附近来回磨蹭，
一声不响。判定条件是「上一个采样点还在预警线之外」。

这一条把预警从 27 条压到 **17 条**，是降噪最有效的一招。

## 五、报警分类：碰到价之后，还要看它怎么走

**不是「碰到价就叫」**，而是碰到之后看行为，因为同样是碰到 64.84，
冲过去站住和冲过去掉下来，是完全相反的两件事。

| 结果 | 判定条件 | 推不推 |
|---|---|---|
| **接近预警** | 价格**穿过**预警线（距关键位 1%），且上一刻还在线外 | ✅ 推 |
| **有效突破** | 收在关键位上方，且**放量**（量比 > 1.2） | ✅ 推 |
| **假突破** | 盘中越过了关键位，但又跌回下方 | ✅ 推 |
| **跌破** | 收在支撑位下方 | ✅ 推 |
| 站上没量 | 收在上方但没量 | ❌ 不推 |
| 受阻回落 | 压根没越过去 | ❌ 不推 |
| 探底守住 | 摸到支撑又弹回来 | ❌ 不推 |

后三类是**流水账，不是要用户动手的事**。第二版之所以吵到 73% 的交易日
都在响，一大半就是它们贡献的。

今天这只票会推两条，一前一后：

**第一条**（盘中涨到 64.19 时，提前给你时间反应）：
```
601138 工业富联 · 快到坎了
64.84 是 8/31 的收盘高点，现价 64.19，还差 1%
持仓 100 股 · 成本 61.52 · 浮盈 +4.3%
```

**第二条**（冲到 65.30 又跌回来之后）：
```
601138 工业富联 · 假突破
冲到 65.30 越过 64.84（8/31 收盘高点），没站住
现价 63.55，已从高点回落 2.7%
持仓 100 股 · 成本 61.52 · 浮盈 +3.3%
```

美股盘后的推送要多一行时段标注：
```
RKLB · 跌破  [盘后]
跌破 62.30（8/20 的低点），现价 61.85
盘后流动性低，明早开盘可能反向
```

### 5.1 盘中判定跟回放的区别（实现时最容易翻车的地方）

上面的回放用的是**完整日线**，而盘中拿到的数据是**残缺的**——当天还没走完。
两个地方必须特殊处理，否则实盘表现会跟回放对不上。

**（一）盘中最高价从哪来**

「假突破」的判定要用当天的盘中最高价，不能只看现价：

- A 股：全市场快照 `stock_zh_a_spot` 直接给「最高」字段，用它。
- 美股：把当天所有 1 分钟线的 `high` 取最大值。

**（二）盘中量比不能直接跟 20 日均量比**

「有效突破」要求放量（量比 > 1.2）。但盘中成交量是累计值，
上午 10:00 的时候只跑了半小时，直接除以 20 日均量**永远偏低**，
结果就是「有效突破」这一类**永远判不出来**。

必须按已开盘的时间比例折算：

```
盘中量比 = 当前累计成交量 / (20 日均量 × 已开盘分钟数 / 全天交易分钟数)
```

全天交易分钟数：A 股 240 分钟（4 小时），美股 390 分钟（6.5 小时）。

开盘头十几分钟这个折算很不稳（分母太小，量比会剧烈跳动），
所以**开盘前 15 分钟不做「有效突破」判定**，只判「假突破」和「跌破」。

## 六、防刷屏

现有 `watch_positions` 的设计哲学是「**没事就说没事，不制造噪音**」，
盯盘更得守这条——一个吵的提醒工具，用户两天就静音了，等于没有。

| 规则 | 值 |
|---|---|
| 同一个位的**到位判定**，多少个交易日内不重复 | 5 个交易日 |
| 同一个位的**接近预警**，多少个交易日内不重复 | **10 个交易日**（预警冷却更长） |
| 触发要连续几个采样点确认（防一根插针的假信号） | 常规 2 个 / **盘前 3 个** |
| 每天每只票最多几条 | 4 条 |
| 每天总共最多几条 | 25 条 |

去重状态写本地 JSON 文件，**进程重启不会重复轰炸**。

**实测频率**（601138 近 45 个交易日，单只票）：

| 方案 | 预警 | 到位 | 合计 | 多少天在响 |
|---|---|---|---|---|
| 不预警 | 0 | 18 | 18 | 31% |
| 提前 1%，区间内就报 | 27 | 18 | 45 | 53% |
| **提前 1%，只在穿越那刻报** | **17** | **18** | **35** | **47%** |

最终方案：单只票平均**每天 0.78 条**，7 只持仓摊下来每天 5~6 条。
比不预警的版本吵，但换来了「提前 1% 就知道」——这是用户明确要的。

## 七、配置与数据写入

### 7.1 新增环境变量

```bash
TG_BOT_TOKEN=...          # 复用用户已有的 Telegram 机器人
TG_CHAT_ID=...            # 推给谁
TG_PROXY=...              # 可选，服务器上已有代理
WATCHDOG_INTERVAL=60      # 每轮间隔秒数，默认 60
WATCHDOG_WARN_DIST=0.01   # 预警线距关键位多远，默认 1%
WATCHDOG_PREMARKET=1      # 盘前要不要盯，默认要（门槛自动提高）
```

代码**不假设这些键已经存在**——用户已有的 Telegram 机器人配置在别处，
需要他把 token 和 chat id 填进本仓库的 `.env`。缺配置时进程应当
**明确报错退出**，而不是静默不推送。

### 7.2 不新建数据库表

关键位每天开盘前算一次放内存，去重状态写本地 JSON 文件。

**本仓库「只写 user_watchlist / user_positions / analysis_history
三张表」的规矩不破**，也不用碰 tt-data-hub 的 schema。

盯盘进程对数据库**只读**（读 `user_positions` 和 `stock_ohlcv_daily`），
走 `readonly_user`。

## 八、测试策略

`core/levels.py` 是纯函数（进去一串日线，出来一组价位，不碰数据库、
不发请求），所以能直接拿固定数据测：

1. **回放测试**：把 601138 近 45 个交易日灌进去，断言今天会在 64.84
   触发「假突破」——这是本设计的验收标准，写死在测试里。
2. **插针测试**：构造一根「最高价很高但收盘吐光」的 K 线，
   断言它**不会**被当成关键位。这是第一版翻车的地方。
3. **去重测试**：同一个位连续触发，断言 5 个交易日内只推一次。
4. **降噪测试**：断言「探底守住」「站上没量」不产生推送。
5. **实时接口打桩**：跟 `tests/conftest.py` 现有做法一致，

## 九、明确不做的（YAGNI）

- **不盯 155 只自选**。第一版只盯持仓，跑稳了再说。理由：美股是按票拉的，
  156 只要 6 分钟转一圈，且有被代理限流的风险。
- **不做成本线和涨停板提醒**。用户明确只要「头顶的坎」和「脚下的坎」。
- **不自动下单**。程序只负责叫醒用户，买卖决定由用户自己做。
- **不建数据库表**。
- **不做夜间静音、不做汇总推送**。用户明确要求夜里全部照推，
  自己在手机上设免打扰。不要自作主张加「攒到早上一起发」的逻辑。
- **不碰 tt-data-hub**。东财源挂掉、美股 09-03 只采到 106 只，
  这两个问题记录在案，但修在那边，不在这里。
